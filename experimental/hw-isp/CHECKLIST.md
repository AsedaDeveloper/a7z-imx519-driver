## B. Make it a proper camera device, stability, hardware blocks, tuning
### B-1 Standard interfaces
- [x] B1 Standard V4L2 node — `sudo v4l2node start` publishes the ISP output (autofocus, white balance, exposure cap) on `/dev/video9` as single-planar YU12 1080p30; a plain V4L2 client with no vendor ioctls read 20/20 frames. Needs a loopback because libisp cannot run outside the streaming process (proof in V4L2_NODE.md). A media-controller topology for sensor/ISP/lens is still not exposed
- [x] B19 Standard apps read the camera with no custom tool — **verified on /dev/video9: `v4l2-ctl` 20 frames, `ffmpeg` h264 1080p, GStreamer `v4l2src`+jpegenc 20 JPEGs, `cv2.VideoCapture(9)` 20/20 at (1080,1920,3), plus `python/a7z_v4l2.py` at 28.1 fps with no dependencies.** Needed Debian's stock gstreamer1.0-plugins-good (Radxa's patched v4l2src fails on any standard device) — see V4L2_NODE.md. Control of focus/exposure through V4L2 is still B2
- [x] B2 Lens as a standard V4L2 control (`FOCUS_ABSOLUTE`) instead of vendor ioctls **Oct 27: done on the node apps use, `/dev/video9`: a 11-line patch to v4l2loopback adds `focus_absolute` (0..1200 = hundredths of a dioptre) and `focus_automatic_continuous`, and `a7zcap` reads them back and moves the lens. Verified as an ordinary user with `v4l2-ctl` (300/700/1100 -> lens 3.00/7.00/11.00 dpt from the frame metadata, reads back, autofocus resumes) and from OpenCV (`CAP_PROP_FOCUS` 500/900 -> 5.00/9.00 dpt); 30 fps, 0 drops. Fixed a race found by the OpenCV run (AUTOFOCUS=0 and FOCUS written back to back). Not done: the kernel `ak7375_act` subdev still has no controls and `/dev/video0`'s `focus_absolute` is still inert, and the fallback with an unpatched loopback was not run. See CONTROLS.md.**
- [x] B3 Device-tree overlay and a service — the overlay is now a plain `.dtbo` so `u-boot-update` puts it on every generated entry (the `.trial` suffix was why `default l0` kept losing the camera, twice in one day), and `a7z-camera.service` brings up the loopback and the supervised feeder at boot. Verified across two reboots: service active, `/dev/video9` present, OpenCV 15/15 frames, nothing typed. See BOOT.md
### B-2 Stability
- [x] B4 Dropped frames — autofocus now encodes every frame it dequeues (no ~1.5 s hole per refocus) and the capture queue is 8 buffers deep (`A7Z_NBUF`): **0 dropped frames in 9.6 min at 1080p30 across 8 refocuses**. Cached buffers / DMA-buf not needed so far; revisit if a heavier consumer is added
- [x] B5 Stall recovery watchdog — `tools/a7zstream.sh` supervises a7zcap (exit 3 = encoder wedged -> reload `sunxi_ve`, exit 4 = capture stalled, other -> retry); verified by killing the process mid-stream and by a busy device. See STABILITY.md
- [x] B6 MIPI link margin — found where the receiver really reports errors: the register the vendor header calls an ECC *count* is the combo-CSI channel-0 **interrupt-pending word** (sticky bits, reset at stream start), and `0x11C` is not a counter at all. Swept 816-1392 Mbit/s: **`ecc_warn` latches at 1344, exactly where the picture first measurably degrades (290 outliers/Mpx vs a floor of 3), `ecc_err`+`frame_sync_err` at 1368 — and the shipped 1296 default already latches `chksum_err` where the stock 816 mode latches nothing.** `tools/link_ladder.py`; `a7zstatus` shows the bits. No driver-side *handling* (the interrupts are never enabled). See LINK.md
- [x] B7 Soak test and regression script — `tools/soak.sh`; 9.6 min at 1080p30 after the autofocus fix: 17900 frames, **min and median 30.0 fps, 0 dropped frames over 8 refocuses**, 0 restarts, 0 errors. Hours-long runs and replug still to do
- [x] B8 Exposure/gain latency compensation per sensor (settings take effect a couple of frames late) **Oct 27: latency measured, 4 frames at 1080p30 (METADATA.md) and used when labelling frames. libisp's own AE loop does not hunt despite it: static scene 85 s with exposure x gain constant (0 reversals); step response (`tools/ae_check.py`, torch on/off at the lens, one trial each way): light on, luma 130 -> 214 -> back to 133 in ~1.5 s, monotonic, no overshoot; light off, luma 38, exposure x gain raised 10x in 6 frames, overshoot to luma 168 (+30%), settled to 131 in ~0.3 s with a ~5% wobble after. A bounded one-off transient, no sustained oscillation. One trial per direction, indoor torch only.**

- [x] B10 Hardware JPEG encoder — works, ~80 fps at 1920x1088, valid JPEG verified (`A7Z_ENC=jpeg`)
- [ ] B11 2D engine (G2D) for scaling / rotation / colour conversion instead of the CPU box downscale **Oct 27: WORKS from userspace, root cause of the earlier "writes nothing" found: `g2d_image_enh.bbuff` must be 1 (0 = constant colour layer). NOT integrated: the only CPU box downscale is the optional USB preview (`A7Z_STREAM_D`), where the G2D would save ~2-3 ms CPU per frame, and it needs the ISP output buffers as dma-buf fds. Left unticked because nothing uses it yet.**

### B-5 Sensor modes and features
- [x] B16 Sensor modes and a clean mode switch — all **seven declared modes verified through the hardware ISP at their rated rate** (720p 84.7, 1080p 60.0, 2328x1748 30.0, 3264x2448 13.4, 3840x2160 18.0, full 9.4 and 15.1), and **switching modes needs no driver reload** (5/5 transitions, including in and out of 16 MP). No new mode was added: the set already covers binned and high-fps. Found the trap that made the fast modes look broken — libisp's ~30 ms auto exposure pins anything above ~33 fps, so 720p85/1080p60 need `A7Z_MAXEXP`. Also: the service's 1080p30 request actually runs the 2328x1748 binned mode through the scaler. `tools/mode_matrix.py`; see MODES.md
- [x] B17 Check whether the IMX519 phase-detect data is usable for much faster autofocus **Oct 27: answer is no, on this stack. The receiver sees one stream only: sampling the combo-CSI packet-header register (`tools/mipi_types.py`) for 8-10 s per mode gave 97-100% RAW10 pixel lines (2328x1748 binned: 2910 B/line; 4656x3496 2-in-1: 5820 B/line) plus frame start/end, all on virtual channel 0, and no embedded-data (0x12) or vendor data type and no second virtual channel in 4.3M-9.1M samples; the receiver is configured for 1 channel (debugfs mpp/mipi). So PD data is not delivered as a separate stream. If the sensor puts PD pixels inside the image, only the ISP sees them (raw is not exposed without the bypass overlay, C1/C4) and Sony does not publish the format. The driver writes 0x3e20/0x3e37/0x3e3b in every mode, which was not tested for effect. Autofocus stays contrast-based.**
- [x] B18 Per-frame metadata — one record per frame (exposure, gain, lens position, colour gains, autofocus flags) in a shared ring `/run/a7zcam.meta` and an optional JSON-lines log, matched to a `/dev/video9` frame by its timestamp: **90/90 frames matched as an ordinary user; recorded exposure correlates 1.000 with frame brightness at offset 0 (-0.76..+0.08 elsewhere)**. Measured the exposure pipeline latency at the same time: **4 frames** at 1080p30. `Camera.read_with_meta()` in `python/a7z_v4l2.py`. See METADATA.md

### C-2 System side
- [x] C7 Run as a normal user instead of `sudo` — udev rules (`tools/99-a7z-camera.rules`) and a group-writable control file: reading `/dev/video9`, `a7zfocus` and a hand-run `a7zcap` (90 frames) all verified as `radxa` with no sudo. The systemd service stays root (module loading, `sunxi_ve` reload). See BOOT.md
- [ ] C8 Thermal and power behaviour in a closed case at full load; clock pinning versus power draw. **Oct 27: open-air part done — 15 min at 4656x3496@15 peaks at 51 C (passive trip 60, critical 110), frame rate flat at 15.1, big cores at the full 2002 MHz. Found that the `power_allocator` governor caps the *little* cluster to 416 MHz (cooling state 8/8) during capture at only ~48 C, well below any trip; harmless here because a7zcap pins to a big core. Still open: no enclosure (the fan ran at 4/4 throughout) and no power measurement (`/sys/class/power_supply` is empty, needs an inline meter). `tools/thermal_soak.py`; see THERMAL.md**
- [x] C9 Accurate timestamps / shared clock — frame timestamps are `CLOCK_MONOTONIC` on both nodes and in the metadata ring, so frames, exposure records and any other log share one timebase; UTC is one offset away (spread 6.3 ms over a run). Measured jitter at 1080p30: **capture side +/-1.1 ms, loopback +/-2.6 ms with occasional 1.2 ms back-to-back pairs** — so take timing from the ring, not the loopback. Found that this board's wall clock is **not anchored** (NTP unsynchronised, clock five days out), so logs must carry the monotonic time plus one external anchor per session. `tools/clock_check.py`; see TIMING.md
- [ ] C10 Dual-camera sync — **not possible on this board (Oct 27).** The Cubie A7Z exposes a *single* 31-pin camera connector, J5 (docs/HOW_IT_WORKS.md); the SoC has three MIPI/CSI ports and the Radxa stock overlay even references csi0/mipi0, but that is a port on other boards in the family, not a second connector here. The overlay declares one sensor (`sensor0`, csi1/mipi1, TWI3, MCLK1). A second constraint applies even with two ports: the 16 MP 2-in-1 mode consumes **both** ISP instances for one camera, so two cameras could not both run at full resolution through the ISP. Needs different hardware (a two-connector board, or a serialiser), so this is parked rather than open.
- [x] C11 One diagnostics tool (drops, link errors, exposure, white balance, autofocus state) **Oct 27: `tools/a7zstatus` (human + `--json`, exit codes) reports service, drops, rate, autofocus, live frame stats and white-balance ratios, temperatures, libisp errors; exposure/gain/lens come from the B18 metadata ring and the MIPI link error bits from B6 (that line needs root); white balance comes from the live frame probe. Building it found and fixed a silent failure: a feeder with no loopback ran "healthy" and published nothing; a7zcap now exits 5 and the supervisor reloads the loopback. See STABILITY.md**
